# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Decodes Nokia NVG files (the Symbian^3 binary vector format) back to SVG. Everything lives in `web/` and is plain JavaScript with no dependencies. There is no build or lint config.
- `web/nvg2svg.js` is the decoder. It works as a classic `<script>` (defines `window.NVG2SVG`) and as a CommonJS module.
- `web/cli.js` is the Node command-line front end (`-o`, `-d`, `-v`). It uses only Node's standard library and must stay cross-platform.
- `web/index.html` is the browser version, a static page. It loads the decoder as a classic script, not a module, so it also works from `file://`. It writes zips itself (stored, no compression).
- `web/check.js` is the regression and fuzz test. It compares the decoder's output (SVG, warnings, error message) for every example with `test/expected/<input name>.svg|.error|.warnings`, and `--fuzz N` checks that N randomly corrupted copies never crash (anything other than `NvgError`). Run it after every decoder change; there is no CI. If an output change is intended, run it with `--update` and review the diff of `test/expected/`.
- `test/expected/` was generated by the original Python decoder (removed; it is in git history before the switch to Node) and verified identical to the JS port on 20,000 fuzzed inputs. `fmt()` deliberately reproduces Python's `"%.4f"`, which rounds exact ties half-to-even (s32/65536 coordinates often hit such ties), so do not replace it with plain `toFixed`.
- `Dockerfile` + `compose.yaml` serve `web/index.html` and `web/nvg2svg.js` with nginx (`docker/nginx.conf`, with a strict CSP) on host port `PORT` from `.env`, which defaults to 8080. `.dockerignore` whitelists only the files that are served.
- `SVG2Binary 1.1/` is the reference encoder, a Windows GUI around `libs/svgtbinencode.exe` from the Symbian^3 SDK. `-v 5` produces NVG. The NVG format was reverse-engineered from this binary.
- `SVG_SVGB_SVG2DAT Converter 1.0/` holds third-party Windows tools (`svg2svgb.exe`, `svgb2svg.exe`) for the older SVGB format, which the decoder does not support yet.
- `examples/` is the regression corpus of real encoder output. Files that start with `CE 56 FA 03` are real SVGB (vector `Python.svgb`; `MoonCalc`, `StarFind` and `SunCalc.svgb`, which only wrap an embedded PNG; `strokes.svgb`) and are currently rejected.

## Commands

```
node web/cli.js examples -d /tmp/out -v          # decode all examples; -v dumps header/offsets/commands to stderr
node web/cli.js examples/Python.nvg -o -         # single file to stdout
node web/check.js examples --fuzz 5000           # regression test against test/expected/ + fuzzing
xdg-open web/index.html                          # browser version, no server needed
docker compose up -d --build                     # serve web/ on $PORT (default 8080)
rsvg-convert -w 384 /tmp/out/Python.svg -o /tmp/py.png   # render to check visually
```

A correct decode prints no warnings and no "unused bytes" notes, which means every path block was consumed exactly.

## Architecture

The comment at the top of `web/nvg2svg.js` is the authoritative format spec. Keep it in sync with code changes.

- `NvgFile` parses the header, the offset vector (u16 absolute file offsets to data blocks) and the command stream. It reads path and paint blocks on demand (`readPath`, `readPaint`).
- `SvgBuilder` replays the commands as a state machine. It tracks fill and stroke paint, opacity, ramp, transform and stroke properties, and emits one `<path>` per DRAW_PATH. Gradients go into `<defs>`, deduplicated by (paint block, ramp block).

Non-obvious format facts (all verified in the decompiled encoder):
- Commands are **variable length**: SET_TRANSFORM (0x08), stroke width (0x09) and miter limit (0x0b) are followed by f32 payloads, so the stream must be parsed sequentially.
- The header scale field is **stale**: the encoder writes the header before computing the scale. The scale therefore comes from the datatype via `PATH_DATATYPES`. Datatype 3 means s32 values ×65536 and is the only datatype the encoder emits in practice.
- SET_COLOR_RAMP (0x06) applies to whichever paint (fill or stroke) was set immediately before it.
- SET_TRANSFORM replaces the current transform; it does not concatenate.
- The gradient matrix is stored row-major (a c e b d f).
- The encoder stores opacity 1 (not 255) for gradient strokes. This is handled as fully opaque.

The encoder always names its output `.svgb`, even when the file is NVG. `examples/circles.svgb` and `examples/transform.svgb` are NVG, and `original/` holds their source SVGs. Rendering a source SVG and the decoded SVG with `rsvg-convert` should give identical output (`magick compare -metric AE`). These two files verify arcs (circles become relative SCCWARC segments, 0x13, plus two trailing junk coordinates) and full-matrix transforms (flags 0).

`examples/strokes.svgb` is real SVGB, because `stroke-dasharray` triggered the encoder's fallback, and the decoder rejects it. Strokes (opcodes 0x05, 0x09–0x0b), partial transforms (translate- or scale-only flags) and radial gradients are still inferred only from decompilation.

## Re-inspecting the encoder

Ghidra is installed at `/opt/ghidra/support/analyzeHeadless`. Wine is not installed, so the encoder cannot be run. These are the key functions in `svgtbinencode.exe`:
- `FUN_00415710`: write order (header → offsets → commands → paths → paints)
- `FUN_004179a0`: header
- `FUN_00411bc0`: commands
- `FUN_0041a780`: paths
- `FUN_00418920`: paints and ramps
- `FUN_00412f10`: transform flags
- `FUN_004166b0`: join/cap values
